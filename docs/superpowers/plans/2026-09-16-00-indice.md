## 2. Reglas de trabajo (sin Docker, un solo proyecto Supabase)

1. **Ramas:** cada PR sale de `master` actualizado: `git switch master && git pull && git switch -c feat/<pista>-<parte>`.
2. **Esquema primero.** Cada pista con tablas nuevas tiene:
   - **Parte A (PR de esquema):** migraciones + pruebas de integración. Se verifican **solo en CI** (base temporal). Al mergear, la Action aplica la migración al proyecto.
   - **Parte B (PR de funcionalidad):** empieza con `npm run db:tipos` sobre `master` actualizado (requiere que la Parte A ya esté aplicada), y después consultas, acciones, pantallas y e2e.
3. **Nadie ejecuta `supabase db push`** desde su computadora después de la Fase 0 (spec §10).
4. **Pruebas:**
   - `npm test` (unitarias) corre en local.
   - `npm run test:integracion` y `npm run test:e2e` corren **solo en CI**. Abortan si `NEXT_PUBLIC_SUPABASE_URL` no es local.
   - Para ver el resultado: `git push`, abrir el PR y revisar el job **base-de-datos**.
5. **Migraciones:**
   - Se crean con `npx supabase migration new <pista>_<descripcion>` (no requiere Docker).
   - Antes de mergear: `git rebase master`.
   - Si en `master` ya hay una migración con timestamp **posterior** al de la tuya, renombrá tu archivo con un timestamp nuevo: `supabase db push` rechaza migraciones anteriores a la última aplicada, y el rebase no cambia el nombre del archivo.
6. **Commits:** pequeños, en español, con prefijo (`feat:`, `test:`, `fix:`, `chore:`, `docs:`).
7. **Revisión:** cada PR necesita la aprobación del otro colaborador y CI en verde.

### 3.3 Server Actions

- **Con formulario** (`useActionState`):
  `export async function accion(_previo: Resultado<T> | null, formData: FormData): Promise<Resultado<T>>`
- **Sin formulario:**
  `export async function accion(entrada: unknown): Promise<Resultado<T>>`
  Siempre se valida `entrada` con zod antes de usarla.
- **Orden de pasos:**
  1. `perfilParaAccion(...roles)`: si devuelve `fallo`, retornarlo tal cual.
  2. Validar con zod; si falla, `fallo('mensaje', campos)`.
  3. Escribir.
  4. `revalidatePath('/<seccion>')`.
  5. `exito(data)`.
- **`redirect()`** nunca va dentro de `try/catch`.

### 3.4 Base de datos

- Nombres en español, `snake_case`, igual que el spec §3.
- **Toda FK a `perfiles` usa `on delete cascade`.** La app nunca borra perfiles (solo desactiva); el cascade existe para `limpiar-datos-demo`.
- **RLS activado en toda tabla nueva**, con políticas `to authenticated` que incluyan `(select public.soy_activo())`.
- **Funciones auxiliares:** `security definer` + `set search_path = ''` + nombres con esquema. Excepción: el procedimiento `cerrar_comidas_vencidas` (spec §6.3).
- **Errores propios:** códigos `MOL01` (comida cerrada o fuera de ventana), `MOL02` (Director activo mínimo), `MOL03` (regla de mensajes o reacciones), `MOL04` (nota inválida). Cada pista nueva usa el siguiente libre y lo anota aquí.
- **Firmas SQL de Comidas (contrato 02-A → 02-B y 06):**
  - `guardar_seleccion(p_fecha date, p_comida tiempo_comida, p_estado estado_comida, p_nota text) returns void`
  - `volver_a_plan(p_fecha date, p_comida tiempo_comida) returns void`
  - `comida_editable(p_fecha date, p_comida tiempo_comida, p_ahora timestamptz default now()) returns boolean`
  - `nota_valida(p_estado estado_comida, p_nota text) returns boolean`
  - `PROCEDURE cerrar_comidas_vencidas(p_ahora timestamptz default now())`
  - `comidas_sin_definir(p_fecha date, p_comida tiempo_comida) returns setof uuid` (solo `service_role`)

### 3.5 UI

- Se reutilizan las clases CSS del prototipo, portadas en `app/globals.css` (tarea 10 de la Fase 0). Antes de crear estilos nuevos, buscar la clase equivalente en `docs/prototipo/centro-el-molino.html`.
- Textos en español con **voseo**, como el prototipo ("Iniciá sesión", "Tocá un día").
- Fechas y horas siempre en zona `America/El_Salvador` con `lib/fechas`. **Nunca** `new Date().getDate()` para fechas de calendario.
